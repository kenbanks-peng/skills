03 · Command output

Use only `scripts/dispatch.py` for dispatch operations. Run `--help` or `<command> --help` for phase-specific inputs. Internal modules are not agent commands.

Default JSON is an actionable summary, not full evidence. Keep `record_path`, `evidence_path`, and report `source_path`. Read a specific field or file when needed; do not print whole worker records, note histories, container mounts, or logs. `--verbose` returns complete command evidence. Do not rerun a mutation merely to get verbose output: read its saved evidence instead. Read-only inspect can be repeated with `--verbose`; it does not save fresh observations.

Cleanup and housekeeping summaries include total counts, at most three entries, and a `more` count. Resolve all remaining entries from the saved evidence. An `ok` finish can still have `pending_cleanup`; it is not run closure. See [input/output inventory](io-inventory.md) for formats, size budgets, and evidence retention.

05 · 1. Select and launch

Add tasks with clear requirements and acceptance criteria; express ordering with Aven dependencies. Group tasks with epics rather than labels. Ask before initializing a missing Git repository.

Run startup only after dispatch is requested, in the original host terminal, never during intake:

```sh
aven list --ready
aven context APP-1234
python3 <skill-directory>/scripts/dispatch.py startup APP-1234
python3 <skill-directory>/scripts/dispatch.py launch APP-1234 \
  --base main \
  --check '["python3", "-m", "unittest"]'
```

Startup and launch must use the same run ID. It defaults to the command's task ref; for multiple worker tasks, pass `--run-id <stable-id>` to startup and every launch. Launch verifies the saved run record, not the Aven tab. Closing that tab does not block worker launch or resume. Resume uses the worker's saved run ID. Reuse exact tab identity rather than matching by label. Preserve the returned `record_path`. For interrupted startup, load [runtime.md](runtime.md#dispatch-startup-and-aven-tab).

Repeat `--check` for required checks. Put task requirements in Aven rather than separate prompt fields. Pass `--platform darwin` when macOS workers are requested; otherwise launch defaults to `linux`. Let the script manage configuration, runtime selection, and UI routing. Treat script failures as blockers.

Require launch `ok: true`: the script confirms worker identity, sets active when needed, and reads Aven context to confirm the status. It saves the worker in the run index. If activation fails, use `dispatch.py resume <task-ref>`; it reads live status before any retry and never creates a replacement. Append a `DISPATCH:` note linking the returned handle and recovery record; use `tasks` for selective notes.

3. Launch

Set `skill_dir` to this skill's absolute directory, `base` to the integration branch, `group` to the unique name, and `assignment` to the assignment text. The assignment must name the task and all fields above, instruct the worker to follow its worker contract, and say to stop after reporting.

```sh
tuios fan 1 \
  --agent "pi --append-system-prompt '$skill_dir/worker.md'" \
  --base "$base" --name "$group" \
  --grants read,write --wait --json "$assignment"
```

The inner quotes protect spaces in the skill path. If it contains a single quote, construct a correctly shell-quoted agent command instead. Add pi model flags only when requested or required by project policy. Pass needed environment variables with `--env NAME`; do not put secrets in prompts or notes.

Repeat for each independent task. One fan of one per task keeps assignment, repair, verification, and cleanup separate. This uses tuios's native launch and prompt gate; no dispatch wrapper is needed.

4. Wait and review

Address every pane with its saved session and full pane ID:

```sh
tuios wait-for agent-state -s "$worker_session" -w "$worker_pane" \
  --until done,needs_input,errored --timeout 600000
```

Give the enclosing tool more than 600 seconds, or use a shorter bounded wait. A timeout is not worker failure. Read current state before the next wait. Handle a finished or blocked worker instead of waiting on that same state again. For several workers, wait on the exact unresolved set with the fleet selectors; exclude workers already under review.

tuios state is a turn signal, not task acceptance. Read the current task context and the worker's matching `RESULT:` or `BLOCKED:` note. Match task, run/group, branch, and full commit SHA. Use `aven context`'s note-read command when the required note is omitted.

- The worker's full commit SHA and clean worktree.

5. Integrate and complete

Integrate one task at a time, with no concurrent Git writer on the target branch.

1. Confirm the worker is at rest, has no running tools or child agents, and has no queued instruction that can resume writes. Keep it at rest through integration. Inspect `tuios queue ls -s "$worker_session" -w "$worker_pane"`; remove only your own obsolete entries.
2. Pin the reviewed full SHA. Immediately before merge, confirm the worker branch still points to it and the worktree is clean. Any changed SHA requires review again.
3. Confirm the main checkout is still clean on the intended integration branch. Merge through tuios:

   ```sh
   tuios ship merge -s "$worker_session" -w "$worker_pane" --into "$base"
   ```

4. Confirm the reviewed SHA is an ancestor of the resulting base. Run the required checks against that integrated revision in the main checkout. Save the full base SHA and check outcomes.
5. Append `VERIFIED:` to Aven with run/group, reviewed SHA, integrated base SHA, acceptance decision, and check evidence. Only then mark the task done and read back its status.

Keep the task active if review, merge, or checks fail. Record the blocker, owner, and next action. A merge conflict is a repair in the worker worktree, followed by new checks and review. A merged change with failing integrated checks is delivered but unverified; record both facts. Do not reset the user's base to hide it.

6. Clean up and close

After acceptance, end the exact pi worker and confirm it and its child processes stopped before removing its worktree. At an unblocked, empty pi prompt, `ctrl+d` exits pi; send it only to the saved pane. Use `tuios wait-for window-exit` with that session and pane when pi is the pane's main program, or confirm pi exited back to its shell. A missing pane alone is not exit proof. If writer identity or exit is uncertain, retain the worktree and report pending cleanup.

Inspect tracked, untracked, and ignored files for material artifacts before removal. Preserve logs or outputs needed for handoff outside the worktree. Then use:

```sh
tuios worktree rm "$worker_session"
```

Use normal removal, without `--force` or automatic stash. tuios retains the branch. Retain dirty or uncertain resources with an owner and next action. A cleanup failure does not undo accepted delivery; note it separately on the done task.

Gaps / differences

Completion and cleanup are separate: tuios writes VERIFIED and marks done before worker shutdown and cleanup. No single finish helper, explicit delivered/task_complete/pending_cleanup/housekeeping result fields, known-prompt archive, finish-blocked.md, or finish-owner recovery contract. Both retain unsafe resources; tuios uses normal worktree removal and retains the branch.

10 · 5. Close or hand off

Query ready work again with the run's filters. Create or reuse follow-ups and separate current-run work from deferred backlog. Run explicitly required final-run checks against the final pinned base; use `dispatch.py recover verify --help` if a separate check is needed. Do not repeat task checks as an extra run-wide gate.

Before final handoff, reconcile every tracked task against saved records and Aven context, including done tasks with pending cleanup; see [recovery.md](recovery.md). Never bulk-mark active tasks done. Append one `SUMMARY:` on the epic or designated task containing:

- Delivered work and checked revision.
- Unresolved work and owner/next action.
- Every remaining active task with its blocker, owner, and next action, or explicitly none.
- Pending resource cleanup.
- Housekeeping, separately.
- Saved record/evidence links for resuming work and cleanup of completed tasks.

On a blocker, retain a BLOCKED report locally if Aven fails and restore durable reporting before integration or completion. Use the `tasks` policy rather than rendering note templates. For a file-backed handoff:

```sh

```
